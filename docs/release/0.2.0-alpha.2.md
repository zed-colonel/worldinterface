# WorldInterface 0.2.0-alpha.2

Release identity: **0.2.0-alpha.2 / v0.2.0-alpha.2**.

Changes since alpha.1 use the WSP-02 merge `55c8020` as the baseline.
All eight new-runtime crates (worldinterface-protocol, capability, domain,
storage, worker, ingress, egress and runtime) advance together, with exact internal
requirements. Use `=0.2.0-alpha.2` for every direct WorldInterface requirement;
update the standalone `examples/downstream-consumer` copy and regenerate its lock.
Rust 1.89.0, Linux x86_64 GNU, Apache-2.0 and crates.io ActionQueue `=0.3.0`
remain the release profile. The legacy 0.1.x root workspace is unchanged.

## Store compatibility and required consumer changes

**An alpha.1 store must be recreated under alpha.2. A store opened by alpha.2
cannot be read by alpha.1. No migration or rollback compatibility is provided.**
The stores are not interchangeable in either direction. WSP-03 added
`effect_instances`, `effect_owner`, `effect_requests` and `worker_reserved` tables
and indexes; WSP-04 added `flow_pending_global`. Full-schema validation rejects
incompatible stores even though the Flow schema version remains 1. Recreate the
WI stores for alpha.2 rather than opening an alpha.1 bundle or attempting rollback.
This warning also ships in the packaged descriptor and external consumer handoff.

`worldinterface_domain::effect::EffectState` adds public
`ledger: Option<(u64, ContentHash)>`. Explicit struct literals need that field.
Newly constructed default state uses `None`; retained state must preserve its
actual ledger value. Do not clear the field on a snapshot. Version-3 journal
entries fence the tenant revision, retained intent count, previous entry hash and
exact command read set. Historical version-1/2 entry replay remains supported
within the current store implementation; it does not provide cross-release store
migration. `ValidatedEffectCommand::base_digest()` now identifies the journal
fence and command read set, rather than always hashing the complete state.
Use the added `scope()`, `apply_to()` and `effect_action_scope()` APIs for bounded
command validation. `legacy_ledger()` derives the shared ledger seed from a
complete historical projection. An optimistic conflict returns `None` from `apply_to()`;
re-read and revalidate rather than reusing an earlier state/digest.

Storage adds trusted-host `effect_action_snapshot()`, `effect_intent_snapshot()`
and `effect_owner_snapshot()` lookups. Bounded snapshots still carry the shared
journal fence; hosts remain responsible for authentication and authorization.
Flow scheduling adds `PendingFlow`, `flow_pending_global_page()`,
`flow_pending_run()` and `flow_scan_bounds()` (the maximum run rowid).
**Call `flow_prepare_scheduling()` before direct
`flow_pending_global_page()` use.** `QueueEngine` bootstrap performs this
preparation automatically; calling the page API first returns a typed error.
Rowid cursors are disposable within one open host session.

`EvaluationVerifier::verify()` and `authorize()` no longer take a time argument.
`EvaluationAuthority<A, S>` no longer takes a clock field or clock type parameter;
packet acceptance has no calendar expiry. Remove those arguments from host
composition; dispatch and ordinary qualification still enforce their own time bounds.

`worldinterface_runtime::aq_adapter` exposes `TickDiagnostics`, `ReconcileWork`
and `RECONCILE_ROWS_PER_TICK`, with measurements in
`QueueEngine::tick_diagnostics`. Reconciliation validates at most eight pending
Flow rows per tick, prioritizing indexed changed-task hints while progressing a
finite background recovery pass. Completed history and history-only tenants no
longer consume that page bound. Full validation and index preparation remain
startup work. `IngressDeliveryHandler::with_clock()` optionally installs a trusted
host clock shared with admission, dispatch and AQ; the default remains system time.
Provider and task input cannot supply the clock.

## Supervisor boundary and WI-WORKER-G5

Alpha.2 is the first release carrying **WI-WORKER-G5**, separate from the original
55-case, ten-gate embedded worker milestone. Six supervisor cases WP-035–040
establish authenticated interface and durable reconciliation evidence only.
The packaged handoff retains that separate supervisor section, marks
`supervisor.available_since` as `0.2.0-alpha.2`, and includes eleven gate records.
Closure is effective only on reviewed merge with adopted checks. Actual Kata
lifecycle, backend durability, image compatibility, deployment controls and
isolation qualification remain Exoskeleton-owned. Ordinary use, production
credentials and remote-provider qualification remain disabled.

The public `worldinterface_worker::supervisor` protocol exposes `Command`,
`Inspect`, `Record`, `Session`, `Grant` and `SupervisorHandler` for closed lifecycle
operations `stop`, `replace` and `recover`. Implement `SupervisorHandler` in an
operator-owned service outside the target lifetime. This introduces no lifecycle
operation or instance-control authority to `WorkerPort` and no engine client in WI.

The Unix `worldinterface_runtime::supervisor` API provides `Server`,
`ChannelPolicy`, `PrivateChannel`, `Client`, `SupervisorConnector` and
`descriptor(operation)`. Trusted host composition provisions private anonymous
Unix channels with exact server-owned principal, tenant and grants. Keep channels
away from workers and guests; requests cannot choose authentication identity.
Revoke the policy to fence submit and inspect. After WI restart or transport
failure, provision a fresh channel and inspect the same stable command key.

`PrivateChannel::serve_one` takes a host clock function so authorization uses the
time after frame receipt. Transient backend inspect errors remain recoverable
after the dispatch deadline.

Open `Server` on separate durable operator-owned storage outside `StoreBundle`
and the guest filesystem. Its journal persists complete command bindings before
acceptance/dispatch and immutable terminal observations before exposing them.
Acceptance is pending work; only authenticated authoritative stable-key inspect
establishes completion. A lost reply does not establish admission or rejection.
The consumer backend must inspect across ambiguous dispatch and ensure rejection
excludes later activation. Restarted records never dispatch again; preserve the
journal and reconcile rather than erasing it to retry. `SupervisorConnector`
returns `Uncertain`, then drives AQ reconciliation through authenticated inspect
while retaining the original receipt. No callback or application acceptance is
implied. Handler code is trusted host code, with engine-specific cancellation and
process isolation owned by the consumer. See the runtime README for exact bounds.

Additional fixes validate lifecycle target/operation agreement, bound recovery
work, and harden Linux process ownership during descendant discovery, reaping and
cleanup. The supervisor fixture models guest loss in a separate process with
independently retained records; it does not qualify a VM/container boundary.

## Tests in archives and repository

`package-tests.json` is the exhaustive target inventory. Every archive runs
explicit library unit tests and doctests. Packaged integrations are protocol
`control_plane`, capability `scope`, domain `control_plane`, storage `continuation`
and `worker`, worker **`supervisor`**, and runtime `worker_artifact_crash`,
`worker_artifact_validation` and **`supervisor_consumer`**. The latter is the public
supervisor implementor/consumer route; its presence does not make the repository
supervisor campaign package-local. Storage's C fault injector and retained shared
fixtures are included with authoritative byte checks.

Repository-only integrations include protocol `canonical`/`ingress`, capability
`flow_registry`, domain `developmental`/`flow`/`transitions`, storage
`control_plane`/`flow`/`stores`, ingress `lifecycle`, egress `domain`, worker
`contract`/`evidence`, and all remaining runtime targets, including
**`worker_supervisor`** and **`worker_campaign`**. Those require repository
conformance, sibling support or the exact committed evaluation packet. They run
through `foundation-test` and `runtime-test` before packaging; archive tests do
not replace their campaign evidence. The inventory names every target explicitly.

`dependencies_digest()` still embeds `release/repository-Cargo.lock`, byte-equal
to the runtime repository lock. Cargo normalizes each archive's own `Cargo.lock`;
its digest is independently recorded in the manifest and consumer handoff.

## Consumer and worker programs

Copy `examples/downstream-consumer` outside the checkout, then run:

```sh
export WI_WORKER_BUILD_ROOT="$(pwd -P)"
export CARGO_HOME="$WI_WORKER_BUILD_ROOT/cargo-home"
export CARGO_TARGET_DIR="$WI_WORKER_BUILD_ROOT/target"
mkdir -p "$CARGO_HOME" "$CARGO_TARGET_DIR"
export CARGO_HOME="$(cd "$CARGO_HOME" && pwd -P)"
export CARGO_TARGET_DIR="$(cd "$CARGO_TARGET_DIR" && pwd -P)"
export RUSTUP_TOOLCHAIN=1.89.0
export CARGO_BUILD_JOBS=8
cargo +1.89.0 fetch --manifest-path Cargo.toml
cargo +1.89.0 run --locked --manifest-path Cargo.toml
cargo +1.89.0 metadata --locked --format-version 1 > consumer-resolution.json
```

There are exact registry requirements, no path dependencies or patches, and a
standalone workspace. Inspect `manifest_path` for the resolved runtime registry
package and read its `release/handoff.json`, `release/gates/` and lock snapshot.
For a post-publication check use crates.io directly, with no preparation source
replacement. Preserve the generated consumer lockfile and resolution report.

The exports canonicalize paths before Cargo sees them, including an existing
symlink at `cargo-home` or `target`. Preserve those canonical exports for the
worker install; preparation records them in the build environment.
Preparation also canonicalizes temporary-directory environment variables for
repository gates, preserving the runtime store's rejection of symlink components.

Build both worker executables using the same explicit recipe as preparation.
After the fetch above, replace inherited Rust flags with path remappings. Map
each registry source directory, including its registry-id suffix, to the same
logical root; mapping only `registry/src` would retain the variable suffix.
Map staging and target paths too. Map the sysroot's Rust source directory to
`/rustc/<commit-hash from rustc -vV>`, which also matches builds without rust-src
installed. ASCII 31 separates flags so paths can contain spaces. Specific source
mappings come last:

```sh
unset RUSTFLAGS
export CARGO_ENCODED_RUSTFLAGS="$(python3 - <<'PY'
import os
import re
import subprocess
from pathlib import Path
home = Path(os.environ['CARGO_HOME'])
roots = sorted(p for p in (home / 'registry/src').iterdir() if p.is_dir())
assert roots, 'fetch the registry consumer first'
sysroot = Path(subprocess.check_output(['rustc', '--print', 'sysroot'], text=True).strip()).resolve()
rustc = subprocess.check_output(['rustc', '-vV'], text=True)
commit = re.search(r'^commit-hash: ([a-f0-9]{40})$', rustc, re.M)[1]
mappings = [(Path(os.environ['WI_WORKER_BUILD_ROOT']), '/wi/build'),
            (Path(os.environ['CARGO_TARGET_DIR']), '/wi/target'),
            *[(p, '/wi/registry') for p in roots],
            (sysroot / 'lib/rustlib/src/rust', '/rustc/' + commit)]
print('\x1f'.join(f'--remap-path-prefix={source}={dest}' for source, dest in mappings))
PY
)"
cargo +1.89.0 install --locked --version '=0.2.0-alpha.2' \
  --target x86_64-unknown-linux-gnu --profile release \
  --bin wi-process-fixture --bin wi-process-reaper \
  --root "$WI_WORKER_BUILD_ROOT/install" worldinterface-runtime
sha256sum "$WI_WORKER_BUILD_ROOT/install/bin/wi-process-fixture" \
  "$WI_WORKER_BUILD_ROOT/install/bin/wi-process-reaper"
```

The producer executes this route offline through the exact archive registry and
records both digests and sizes in external `consumer-handoff.json`. That record
binds the descriptor, commit, archive hashes, repository and packaged lock hashes,
consumer lock, toolchain, target, profile, path-remapping recipe and actual worker
build environment, including its disposable Cargo home, sysroot, rust-src
availability and encoded flags. The recipe replaces inherited `RUSTFLAGS` and
`CARGO_ENCODED_RUSTFLAGS`. Registry and staging paths are canonicalized before
Cargo runs; preparation and verification refuse workers containing the recorded
build, Cargo-home, target or sysroot paths. Registry
location, staging paths and the sysroot location do not affect the expected
worker digests. Executable digests apply
to that build environment, including its system/linker; they are not universal
reproducibility promises. Compare a consumer's digests under the recorded recipe
and environment, and retain its own measurements if the environment differs.
The operator relays the exact `consumer-handoff.json` bytes and its manifest
SHA-256 through the map's published record to EXV-27; see staging step 4. Consumers
with crates.io-only network access receive that file as an input, verify its
trusted digest, and compare its archive hashes to their registry lockfile.
